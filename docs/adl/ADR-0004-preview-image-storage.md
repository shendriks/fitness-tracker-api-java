# \[ADR-0004\] Store GPS Track Preview Images in the Database

## Context and Problem Statement

When a user uploads a GPX track, the system generates a compact visual preview of the route. This preview is intended for
quick display in lists without client-side rendering of heavy maps.

## Considered Options

* Store preview PNGs on the filesystem and persist file paths in DB
* Store preview images as BLOBs directly in the activity table in the database
* Generate previews on-the-fly for each request without storing them

## Decision Outcome

Chosen option: "Store preview images as BLOBs directly in the activity table in the database", because it provides 
transactional consistency with activity data, simplifies operations, and the images are small thumbnails. 

### Consequences

* Good, because previews are written atomically with activity data; no orphaned files or broken references
* Good, because serving directly from the database keeps reads simple and reduces additional network hops to storage
  backends
* Bad, because DB row size increases
* Bad, because including Base64-encoded previews in list endpoints can inflate payloads

### Notes on Implementation

Implementation details:
* The preview is generated by `RoutePreviewService` using an equirectangular projection to map latitude/longitude to pixels
  and draws a path onto a transparent PNG
* The image is encoded as a byte array and represented in the domain via `Base64ImageData`, with `Base64ImageDataConverter` mapping
  the value to/from the persistence layer
* The preview is small (thumbnail-like) and deterministic for the same input; typical sizes are on the order of a few
  hundred pixels in width/height.
* The image is encoded as Base64 in the `Activity` response DTO
